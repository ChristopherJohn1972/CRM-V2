# CRM v2 — Frontend (Clients & Customer 360)

Production UI for the **Clients / Customer 360** phase of Enterprise CRM v2. This is a
**JavaScript / React** interface that consumes the existing CRM v2 Django backend — it does
**not** create a parallel backend, database, authentication system or business-logic layer.

## Scope

Implements, against the real backend API contracts:

- Internal sign-in (`/api/auth/login`, `/api/auth/me`).
- **Clients** list — search, status / type / segment filters, server-side pagination,
  desktop table + compact mobile cards, and the account number as the link anchor.
- **Add Client** — sectioned flow (type → identity → contact → address → classification →
  assignment). The account number is **generated by the backend** and is never typed or
  pre-supplied by the user. After creation the UI shows the generated number and sends the
  user straight to **Customer 360**.
- **Customer 360** — customer-file layout with a persistent account-number anchor and tabs:
  Overview, Profile (with explicit Save/Cancel + validation + unsaved-changes protection),
  Contacts, Addresses, Relationships, Activities + internal notes, Communications
  (customer-scoped SMS/email history + permission-gated send), Documents (secure signed
  downloads), Accounting (read-only source-of-truth gateway with graceful `unavailable`
  states) and Timeline.
- **Operators / Roles / Rights / Access Review** — internal administration UI. Operators are
  real CRM users; roles are reusable permission bundles; a right is a resource+action pair.
  Operators list, guided Add Operator (identity → organisation → role → live rights preview
  → create, with a single-show temporary password), operator profile (identity edit, role
  assignment, direct ALLOW/DENY exceptions with reason), and a full Access Review screen that
  traces every effective right to its source (role grant or direct exception; **DENY wins**)
  and shows the effective record scope (NONE < OWN < ASSIGNED < TEAM < DEPARTMENT < ALL).

RBAC is enforced **server-side**. The UI only reflects the permission set returned by the
backend on login; `PermissionGate` hides/disables actions for usability only and is never
the enforcement point.

## Quick start

### 1. Backend

Follow the backend README first so the API and database are running, then create an admin:

```powershell
cd "C:\Users\MUTUKU\mu_code\CRM V2\Backend"
.venv\Scripts\python.exe manage.py create_admin --username admin --email admin@example.com --password "ChangeM3!"
.venv\Scripts\python.exe manage.py runserver
```

### 2. Frontend

```powershell
cd "C:\Users\MUTUKU\mu_code\CRM V2\Frontend"
npm install
npm run dev
```

Open http://localhost:5173. The Vite dev proxy forwards `/api/*` to
`http://127.0.0.1:8000` (override with `VITE_API_PROXY_TARGET`, or set
`VITE_API_BASE_URL` to call the backend directly).

### 3. Sign in

Use the internal account created above (or the reserved `test.*@crm-v2.test` test-domain
accounts once seeded). Permissions come from the backend; the UI renders actions
accordingly.

## IAM administration API surface

The Operators / Roles / Rights / Access Review screens consume the backend IAM admin API
(`iam/urls.py`, mounted under `api/`). All routes require `iam.user.manage` /
`iam.role.manage` / `iam.permission.audit` as noted.

| Method | Path | Purpose |
| --- | --- | --- |
| GET, POST | `/api/iam/operators` | List operators / create (returns temp password + rights preview) |
| GET, PATCH | `/api/iam/operators/{id}` | Operator detail (roles + direct permissions + effective scope) / update |
| PUT | `/api/iam/operators/{id}/roles` | Replace assigned role codes (`role_codes`) |
| GET, POST | `/api/iam/operators/{id}/permissions` | List / set direct ALLOW·DENY exceptions (`permission_code`, `effect`, `reason`) |
| DELETE | `/api/iam/operators/{id}/permissions/{code}` | Revoke a direct exception |
| GET | `/api/iam/operators/{id}/access-review` | Full effective-access model (`rights_by_resource`, sources, scope) |
| GET, POST | `/api/iam/roles` | Role catalogue / create (`permission_codes`, `access_policy_codes`) |
| GET, PATCH | `/api/iam/roles/{id}` | Role detail / update |
| GET | `/api/iam/rights` | Rights catalogue (`iam.permission.audit`) |
| GET | `/api/iam/scopes` | Scope reference (NONE…ALL + meanings, `iam.role.manage`) |

Role form scope choices are translated client-side to backend access-policy codes
(`SCOPE_OWN`, `SCOPE_TEAM`, `SCOPE_DEPARTMENT`, `SCOPE_ASSIGNED`, `GLOBAL_ALL`) matching the
seeded `access_policies` rows. Departments/teams have no catalogue endpoint yet, so the
operator organisation section accepts numeric IDs that the backend validates.

## Key UX decisions (per the design spec)

- **Account number is the navigation anchor.** Users never type it; it is displayed as a
  monospace accent and opens the Customer 360 record. The whole table row is not clickable.
- **Profile edit is deliberate**: grouped sections, two-column on desktop, explicit
  Save/Cancel, per-field validation wired to backend `fieldErrors`, and `beforeunload`
  protection for unsaved changes.
- **Sensitive fields** (`tax_identifier`, `registration_number`) render whatever the
  backend returns (masked when the actor lacks `clients.customer.sensitive.read`). The UI
  never unmasks or fabricates them.
- **Accounting is read-only here.** Posting/reversing/reconciling belongs to the Accounting
  module; this view renders `available: false` states with a clear, non-secret message.
- **Loading → skeleton tables; empty → next action; error → actionable message** — backend
  stack traces are never rendered.

## Frontend security rules honoured

- Backend is the source of authorization; `PermissionGate` only changes UI affordances.
- Sensitive fields are only ever displayed as returned by an authorised endpoint.
- File downloads go through short-lived backend-signed URLs (never permanent public paths).
- Communication send actions carry the customer context and are validated server-side.
- Internal notes are visually distinguished from external communications; the Portal Access
  tab does not fabricate portal data and keeps the portal boundary separate.

## Client Portal

The Client Portal is a **separate external experience** owned by the backend
(`/api/portal/*`): separate portal identity, separate JWT type, portal permissions plus
active customer links, temp-credential onboarding, lockout and reset. This repository does
not embed the portal in the internal app; portal screens are a separate build surface so a
portal token is never mixed with internal admin UI.

### Portal API surface (consumed by the separate portal UI)

| Method | Path | Purpose |
| --- | --- | --- |
| POST | `/api/portal/auth/login` | Portal login (temp-credential flag `must_change_password`) |
| POST | `/api/portal/auth/logout` | Portal logout (revokes session) |
| POST | `/api/portal/auth/change-password` | Set permanent password (current + new) |
| POST | `/api/portal/auth/forgot-password` | Request reset token |
| POST | `/api/portal/auth/reset-password` | Reset with single-use token |
| GET | `/api/portal/me` | Profile + effective permissions + linked customer ids |
| GET | `/api/portal/customers` | Linked customers (active links only) |
| GET | `/api/portal/customers/{id}` | Customer summary (denied unless actively linked) |
| POST | `/api/portal/users` | Internal: create portal user (temp password) |
| GET, PATCH | `/api/portal/users/{id}`, `/{id}/status` | Internal: detail / activate / suspend / deactivate |
| POST | `/api/portal/users/{id}/password` | Internal: re-issue temporary credentials |
| GET, POST, DELETE | `/api/portal/users/{id}/customers[...]` | Internal: link / list / deactivate customer links |
| GET, POST, DELETE | `/api/portal/users/{id}/permissions[...]` | Internal: effective grid / ALLOW·DENY / revoke |

Portal tokens (`typ: portal`) are rejected by internal endpoints and internal tokens are
rejected by portal endpoints server-side. Portal access requires **both** an effective
portal permission **and** an active customer link; relationship rank is
`VIEWER < CONTACT < ADMIN < OWNER`, and `DENY` always wins.
